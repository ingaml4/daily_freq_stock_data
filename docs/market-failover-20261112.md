# 东财名单故障与腾讯行情连续性

全市场发现原本已用腾讯批量报价，但启动和名单刷新依赖东财 clist。2026-11-12 东财 502 导致名单刷新失败；此前只加载同日缓存的逻辑还会使次日冷启动失败。本次把名单刷新从实时价格采集拆开，后台探测东财，腾讯按最新可用名单继续报价。

## 数据口径

- 东财负责证券名单。缓存必须经过完整分页、总数、去重、首末页一致性核验。最多使用七个自然日内的完整名单，保留原采集日期和覆盖状态，不能称为当天完整证券清单。
- 腾讯负责新的价格快照。旧名单内价格字段不用于实时信号，逐股源时间、接收时间、交易时段、数值和缺口分别检查。
- 明确指定的板块/股票与名单取并集；没有可用全市场名单时仍采集指定范围，明确全市场覆盖缺失。SH688 在请求前排除，其他指定证券保留观察与权限状态。
- 失败时保留最后一次完整核验名单。东财重新提供完整且一致的分页后才能替换；部分恢复、坏 JSON 或分页漂移不能覆盖可靠缓存。普通故障低频重试，403/429 等访问限制使用更长冷却。
- 双源不可用、腾讯报价过期或缺失都标为降级，不能把 HTTP 200 或进程存活当作数据正常。跨午休、重复源时间及恢复后的首轮不能伪造连续异动。

腾讯快照不是闭合分钟 K 线，也不是逐笔成交；东财成交片段故障不能通过给腾讯快照改名来“恢复大单提醒”。完整分钟与成交片段的可用性单独记录。

## 运行与验收

GitHub 中的 `scripts/full-market-watch.py` 为发布源。Windows 实际运行副本为雪球技能目录下的同名脚本，发布时必须校验两份 SHA256 一致。旧 `sector-routing-review` 原型不能替代正式路径部署。

明日运行必须使用显式 `--date 2026-11-13`；早盘和午盘等待者各写自己的状态，进入采集时共享互斥。检查两个 PID 的真实命令行、目标日期、等待状态及日志，不能只把配置文件存在当作已经运行。

站点板块共享采集器仍每 30 秒调度；用户重点层目标 10 秒，本机飞书消费者独立于雪球串行请求。持续故障仅首次报告，恢复再通知；具体事件按来源时点与类型去重，发送前再核验时效。

开发验收覆盖故障注入、跨日冷启动、损坏缓存、完整恢复、双源故障、超时、交易时段和互斥；另以真实腾讯报价和明确标注的本人飞书系统消息验证连接。盘后测试无法证明明早盘中的延迟表现，首轮运行仍须检查实际周期、源时点和漏采账本。
